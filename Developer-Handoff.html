Booking System

Everything a developer needs to take the working prototype in this project and ship it as a live, production booking platform with real accounts, payments and automated emails.

Prepared for the build team Stack-agnostic spec v1.0

This project contains a fully-functional front-end prototype of the booking system. Every screen, flow and rule is built and clickable. What it does not have yet is a real server — all data currently lives in the browser (localStorage). This document explains the prototype and exactly how to make it production-grade.

The fastest path

The prototype's data layer (assets/booking/store.js) is deliberately written as one clean module with a small, well-named API (Store.createBooking(), Store.isRangeAvailable(), etc.). The data shapes it uses are the database schema. Replace that one file's internals with real API calls and the entire UI works unchanged.

Why Supabase

It gives you Postgres, authentication, file storage and scheduled functions in one place with very little glue code — the closest 1:1 match to what the prototype already does, so the port is fast and cheap to host.

Chosen direction: Netlify (frontend) + Supabase (backend)

The site already deploys on Netlify from the GitHub repo — keep that. Add Supabase for the database, authentication, file storage and scheduled jobs. This is the agreed production architecture.

Why this split: authentication is the highest-risk thing to build by hand, and Supabase Auth handles it for you — password hashing (bcrypt), email verification, password-reset emails, session tokens (JWT) and row-level security. The browser only ever holds a short-lived token; it never sees raw passwords or other customers' data. Cloudflare Workers + D1 was the alternative but gives no built-in auth (you'd hand-roll it), so it was not chosen.

Security non-negotiables

  • Passwords are stored only as salted hashes in Supabase Auth — never in the database you query, never in the frontend bundle. (The prototype's localStorage credentials are demo-only and must be removed.)
  • Row-Level Security (RLS) on every table: a customer can read/write only their own bookings & submissions; only role = 'admin' can read all bookings, manage listings, moderate reviews and edit users/roles.
  • Admin role is a server-side flag on the user row, enforced by RLS policies — not something the client can set. (The prototype's "Make admin" button maps to an admin-only update guarded by RLS.)
  • Secrets (Stripe keys, email/SMS API keys) live in Netlify environment variables / Supabase Edge Function secrets — never in the repo.
  • Serve everything over HTTPS (automatic on Netlify) and set the Supabase anon key as the only key the frontend holds (it's safe to expose; RLS does the protecting).

4 The availability engine

This is the most important logic to port correctly. It already lives in store.js and works as follows:

  • Every booked or blocked day occupies one or two slot cells: AM and PM.
  • A full-day or multi-day booking occupies both slots on every day it spans.
  • A half-day booking occupies only its slot — so an AM booking and a PM booking can co-exist on the same item, same day.
  • blocked dates (maintenance) occupy both slots.
  • Cancelled / declined bookings free their cells.
Must-do on the server: prevent double-booking

Re-check availability inside the booking transaction (the prototype does a client check, but the source of truth must be the DB). Use a Postgres exclusion constraint or a SELECT … FOR UPDATE + overlap check so two simultaneous requests can't grab the same slot. See isRangeAvailable() and occupiedCells() in store.js for the exact rules.

6 Payments (Stripe)

The client wants online card payments. Recommended flow:

  1. Customer submits a booking request → status pending. No charge yet.
  2. Admin approves → backend creates a Stripe PaymentIntent (or Checkout Session) for the deposit (or deposit + hire), and the confirmation email includes the pay link.
  3. On payment_intent.succeeded webhook → mark booking confirmed & paid.
  4. Balance & the refundable deposit can be handled in person, or pre-authorise the deposit with a manual capture PaymentIntent and release it on safe return.
Deposits

Stripe "manual capture" is ideal for a refundable deposit — you authorise the card without taking the money, then cancel the authorisation when the item comes back undamaged.

8 Photo uploads & moderation

  • Prototype stores images as resized data-URLs in localStorage. In production, upload to object storage (Supabase Storage / S3 / Cloudinary) and store the returned URL in the photos array.
  • Keep the client-side downscale step (see readImageScaled() in ui.jsx) to cut upload sizes.
  • Customer submissions start pending; on admin approval, copy/flag the photos into the public gallery (the prototype's setSubmissionStatus() shows the exact behaviour).
  • Always store an EXIF-stripped, re-encoded copy for public display.

Note on the prototype's React

The prototype uses in-browser Babel for zero-build convenience. For production, move the JSX into a proper Vite/Next build (precompiled) — the component code ports over directly. This isn't required for the prototype to run, only for a fast, cached production bundle.
